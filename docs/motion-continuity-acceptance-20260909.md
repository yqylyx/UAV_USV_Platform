# 敌船运动连续性修复与验收

2026-09-09。本轮仅部署本机，未提交或推送；其他本地修改保留。

## 原因与修复

- 护航敌船在追击转围捕后，预留水域边距从 30 m 增到 38 m，运行时直接将位置夹回新边界。10+10 复现 0.1 秒约 7.8 m 侧移，而最高允许位移只有 0.28 m；5+5、15+15、30+30 同样复现。
- 删除运行中的边界投影搬移和护航安全圆搬移。新边距用于规划，当前位置不因阶段变化而改变；位置只由受限航向和标量航速积分。不可执行的危险步长停在原位并重新选择方向，不能瞬移到安全区。
- 围捕子算法还存在分别修改速度分量后强制恢复巡航、把位移改成“离出发点更远”的方向、最后再更换速度方向的问题。改为同一套船头向前的运动约束，移除上述后处理。预览转开始、捕获解除不重置船头和速度。
- 独立 Unity 原先位置快速插值、敌船转向只允许 36°/s，低于算法 70°/s。移动中的目标船由同一平滑位移决定可视船头，停止时限速转向；守卫 USV 的合法倒航不受影响。初始化仍走明确的立即设置接口，不再把运行中的大位移自动视为重置。

运行时安全制动仍有紧急归零路径，用于无可行步长时避免穿越障碍；这不是位置跳变，也不作为围捕成功依据。不能将本次位移连续性通过等同于所有制动工况均已优化到最舒适。

## 测试口径

- 每个敌船逐帧检查：位移 ≤ 最高航速×0.1秒（容许毫米级序列化误差），船头前向分量非负、横向残差 ≤ 3 mm，单步航向变化 ≤ 7.1°。
- 20 组配置分别执行围捕、护航，完整性仍检查真实闭环、所有 USV 船头朝内、意外停滞和阶段回退。运动检查不以任务完成标记代替。
- 固定配置：3+3、4+5、5+4、5+5、6+8、8+6、8+8、10+10、10+12、12+10、12+15、15+12、15+15、18+20、20+18、20+20、20+25、25+20、25+25、30+30。
- 原有一项制动测试跳过 20 帧、只执行一次控制，就要求速度立即降低；改为真实连续执行 20 个步长，并额外检查每步减速度上限，保留闭环后必须减速的原断言。

## 性能对照与边界

1920×1080 测试窗口，独立算法画布 1898×891，硬件报告 NVIDIA GTX 1650。以下操作只作用于隔离的验收浏览器，不是部署改动。

| 30+30 实际运行窗口 | 样本 | P95 回调间隔 | 超过 50 ms |
|---|---:|---:|---:|
| 两套实例共存、总览停放屏幕外 | 1604 | 69.1 ms | 256（15.96%） |
| 删除测试浏览器中不可见的总览实例，窗口 1 | 2491 | 41.9 ms | 26（1.04%） |
| 同上，窗口 2 | 2597 | 47.9 ms | 46（1.77%） |

另一次 CSS display:none 对照，正常/隐藏/恢复 P95 分别为 69.3/69.0/69.2 ms，没有实质改善。不同窗口对应算法不同时间段，数字是工程对照，不是同帧 GPU 精确基准；但移除隐藏实例后的明显下降定位了重要的资源竞争因素。

原因链：App.vue 保持总览运行实例挂载 → UnityRuntimeHost.vue 将其移到屏幕外且 opacity=0.001 → 总览 iframe 未提供渲染暂停接口，继续占用资源。两个实例功能隔离不代表 GPU/主线程资源隔离。

不能把“删除隐藏实例”直接当成产品修复：会丢失总览实例状态，并可能影响设备显示与传感器链路。也没有直接暂停 Unity 主循环，以免停止消息处理。后续安全方案是增加仅控制主显示相机渲染的可见性接口，保留通信/状态更新和按需传感器输出；切回总览先恢复正确尺寸和渲染再显示。该项跨系统总览模块，已向用户询问是否纳入本轮，当前未实施。

因此本轮运动修复通过不等于“30+30 全程无掉帧”通过，也不承诺在所有硬件/屏幕上恒定帧率。全景下远处分组的设备像素尺寸仍需单独优化，不能用裁掉设备或降低渲染分辨率伪造通过。
